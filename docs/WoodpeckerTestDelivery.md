# Woodpecker test delivery runbook

This Kustomize runbook covers the LightRAG fork delivery path for protected `vX.Y.Z-test` tags. The current test deployment opens five numbered suites in the test cluster: namespaces `lightrag-test-01` through `lightrag-test-05`, public hosts `rag-test-01.f123.pub` through `rag-test-05.f123.pub`, and application workspaces `lightrag_test_01` through `lightrag_test_05`.

## Boundaries

- `main` remains the upstream mirror and is not a release source.
- Woodpecker is tag-only for this repository; `master` pushes and PRs do not start LightRAG Woodpecker pipelines.
- Source archives, image records and deployment state use LightRAG-owned COS/registry paths only. All Woodpecker workflows declare `skip_clone: true`; the release-source workflow performs the only manual single-commit clone inside container-local `/tmp`, uploads the source package through MinIO/S3-compatible `mc`, and downstream workflows download that package instead of cloning again. Downstream download steps keep only the compressed source archive/checksum/record in `build/source-artifact/`; consumer steps re-verify and extract into container-local storage, never into the Woodpecker NFS workspace. The Kaniko build consumer uses `/kaniko/lightrag-source` so multi-stage filesystem cleanup cannot delete its context; verify/deploy consumers use `/tmp/lightrag-source`.
- Test environment preparation is part of the `deploy-test` pipeline for every configured numbered instance: it creates or updates the instance namespace, registry pull Secret, Kubernetes runtime Secret, coordination migration Job, storage bootstrap Job, environment snapshot ConfigMap, Kustomize-managed working-storage PVC, and test-only public Ingress before rollout. Object-backed source files and parsed sidecars use COS/S3-compatible object storage plus per-Pod scratch, not a shared input PVC. The pipeline still refuses missing Woodpecker secrets or unsafe storage state without printing secret values.
- Do not claim YAML lint, Kustomize render, or local test results as deployment success. Static validation, local/separate-CI testing, environment initialization and remote acceptance are separate evidence classes.

## Pipeline-managed test environment initialization

The `deploy-test` workflow loops over `LIGHTRAG_TEST_INSTANCES` (default `01,02,03,04,05`) and creates or updates Kubernetes runtime Secrets and the Kubernetes-side test environment for each numbered suite on every `vX.Y.Z-test` deployment attempt while keeping the operation idempotent:

1. It writes the test kubeconfig from global `kubeconfig_test` once, then for each instance creates `lightrag-test-$ID` if missing.
2. It creates or updates `lightrag-registry-pull` from global `DOCKER_USERNAME` / `DOCKER_PASSWORD` inside the current namespace.
3. It creates or updates `lightrag-runtime` from shared Woodpecker repo secrets loaded from `.secrets/test.secrets`, plus the instance-specific API key (`LIGHTRAG_TEST_${ID}_API_KEY`). The Secret includes Bailian/OpenAI-compatible model API key and host, DashScope workspace header, PostgreSQL connection fields, HugeGraph REST/Gremlin endpoints, graphspace, graph and credentials, and S3-compatible object-store endpoint, bucket and credentials from the global COS secrets. The non-secret HugeGraph auth-method metadata defaults to `basic` from the presence of username/password instead of reading a separate Woodpecker secret.
4. Before interrupting any existing service in that namespace, it runs the `lightrag-storage-preflight` Job with the verified release image, the same `lightrag-runtime` Secret, and the same non-sensitive profile environment as the application Deployment. This command checks predictable PG/pgvector and HugeGraph prerequisites without opening durable maintenance, initializing storages, or scaling down the old release.
5. It pauses Service routing, drains existing app Pods, applies the app egress NetworkPolicy, then runs the `lightrag-coordination-migrate` coordination migration Job with the verified release image and the same `lightrag-runtime` Secret. This initializes only the additive coordination schema required by distributed writes.
6. It runs the `lightrag-storage-bootstrap` storage bootstrap Job with the same verified release image, runtime Secret and non-sensitive profile environment as the application Deployment. This explicit maintenance step provisions the PG/vector/status tables, verifies storage contracts and allows HugeGraph schema creation before application writers start; recovery remains manual.
7. It writes `lightrag-test-environment` with the expected test profile: two replicas, one worker per Pod, `PGKVStorage`, `PGDocStatusStorage`, `PGVectorStorage`, `HugeGraphStorage`, `LIGHTRAG_OBJECT_STORAGE=s3`, `LIGHTRAG_SHARED_STORAGE=false`, and matching `WORKSPACE` / `POSTGRES_WORKSPACE` / `LIGHTRAG_DEPLOYMENT_ID` set to `lightrag_test_$ID`. Each instance also uses an isolated object prefix `lightrag/test-$ID/object-ingestion`.
8. It writes the non-secret public entrypoint ConfigMap with host `rag-test-$ID.f123.pub` by default and applies `k8s-deploy/lightrag-kustomize/overlays/test`, creating the ServiceAccount/RBAC, ClusterIP Service, nginx Ingress, NetworkPolicy, working-storage PVC, and `emptyDir` volumes for local input/scratch. No shared `INPUT_DIR` PVC is created for the object-backed acceptance path.
9. It waits for the working-storage PVC to bind, rolls out the two application Pods, verifies image identity, health/authentication and cross-Pod object-backed ingestion/query/retry/delete before restoring Service routing. The ingestion acceptance path is presign → direct S3-compatible PUT → complete → pipeline status/query from another Pod; retry acceptance uses an intentionally failed object-backed text file, overwrites the same object with equal-size valid content, calls `/documents/reprocess_failed`, waits for the original track to recover, then requests object-backed delete with source/artifact cleanup.
10. After routing is restored, it verifies the external debug entrypoint for that instance: `/health` returns 200, `/webui` is reachable, a protected API endpoint rejects unauthenticated and wrong-key requests, and the same endpoint accepts the instance's API key. The same Ingress exposes the API, admin WebUI and query workspace paths; the application API key remains required for protected routes.

The pipeline does not run repository tests and does not perform destructive data recovery or rollback. Existing storage fences, unknown writers, incompatible profiles or failed acceptance still stop the deployment for operator investigation. Instance-specific evidence is written under `build/release/instances/$ID/`, with one summary line per instance appended to `build/release/deployment-results.jsonl`.

## Release flow

1. Push/PR to `master`: no LightRAG Woodpecker pipeline is selected. Keep backend pytest, frontend Bun tests, frontend typecheck/lint/build scripts and external integration tests as local or separate-CI evidence.
2. Protected tag `vX.Y.Z-test`: the source workflow performs the only clone into container-local `/tmp`, runs delivery static checks, verifies repository/tag/commit/master ancestry, archives the cloned source, uploads the archive/checksum/record to the LightRAG COS path with `mc`, then downstream workflows download the archive from MinIO/COS to build and verify `docker-hub.f123.pub/lfun/lightrag` and deploy by digest to every configured numbered test suite with pipeline-managed Secret/namespace/PVC/Ingress preparation, Kustomize and `kubectl -n "$NAMESPACE" apply -k "$OVERLAY"` (the namespace-scoped form of `kubectl apply -k`), keeping Service routing paused per namespace.
   - The release-source step follows the working `../haier-demo` pattern: internal CI tools image, `git init`, no tag/submodule/LFS fetch, `--depth=1` for `CI_COMMIT_SHA`, and retry logging. It is implemented as a normal step rather than top-level `clone:` because strict Woodpecker lint only accepts server-allowlisted clone images. The Git worktree stays under `/tmp/lightrag-release-source`, not the Woodpecker NFS workspace, so `git reset --hard` does not materialize the repository through the shared workspace mount.
   - Downstream workflows keep the workspace artifact small: `download-source` stores only `source.tar.gz`, `source.tar.gz.sha256` and `source-record.json` under `build/source-artifact/`. The Kaniko build step re-checks the checksum and unpacks to `/kaniko/lightrag-source`, while image verification and deploy steps unpack to `/tmp/lightrag-source`, before executing repository scripts. Source extraction therefore no longer creates thousands of files under `/woodpecker/src`, and Kaniko does not delete its own build context between stages.
   - Image building is `scripts/ci/build-image.sh` inside the digest-pinned internal Kaniko debug image. It follows the working `../haier-demo` shape: registry auth is written only inside the step, cache layers go to `docker-hub.f123.pub/lfun/cache-lightrag`, Kaniko logs stream to Woodpecker stdout, `--snapshot-mode=redo` avoids full content hashing on large Python venv layers, and the produced image is labeled with the source commit. The Dockerfiles default Debian apt sources to Tsinghua before `apt-get update`, default Python dependency installs to the internal f123 PyPI mirror, keep `uv.lock` registry/artifact URLs on that mirror so frozen `uv sync` does not use `files.pythonhosted.org`, and default Bun/npm installs to `registry.npmmirror.com`. The Woodpecker release build does not install Rust/Cargo toolchains and does not run the network cache helper for spaCy/GitHub downloads; it copies the committed tiktoken BPE cache from `docker/tiktoken-cache/` so API startup never fetches tokenizer data at runtime.
   - Image verification is `python -m scripts.ci.delivery resolve-image`, which resolves the registry digest and checks the image config revision label against the release commit.
   - Deployment is `scripts/ci/deploy-test.sh` inside the Kubernetes-capable CI tools image; it follows the haier-style shell-script deployment/status pattern, consumes `build/release/image.env` produced from the verified image record, writes kubeconfig from the global `kubeconfig_test` secret, prepares `.secrets/test.secrets`-derived shared runtime configuration, numbered API keys, global COS-backed object-store settings and the non-secret public debug host, runs a non-disruptive storage preflight Job before pausing traffic, runs the coordination migration Job and storage bootstrap Job with terminal-state polling for both `Complete` and `Failed`, applies the Kustomize overlay, waits for rollout, verifies `/health`, `/webui` and protected API behavior through each public Ingress, and prints Deployment/Pod/Service/Ingress status.
3. Verify both Pods' `imageID`, per-Pod health and authentication behavior, plus cross-Pod presigned object upload, pipeline status, query, retry and object-backed delete with unique test documents for each numbered suite.
4. Restore Service routing for an instance only after that instance's acceptance succeeds.
5. Tags `vX.Y.Z-pre` and `vX.Y.Z` publish and verify images but do not deploy.

A plain `master` push does not start Woodpecker by design. To exercise the build and deploy chain, create a protected `vX.Y.Z-test` tag after the scoped registry, COS, kubeconfig and `.secrets/test.secrets`-derived repository secrets are in place.

## Failure and rollback

If a release lock, old writer shutdown, storage fence, pending operation, image identity or acceptance check is uncertain, leave routing closed and preserve evidence. Do not force delete Pods, clear claims, run business bootstrap/recover or automatically start old writers. A rollback is a manual maintenance operation after operators verify no writes are active and the storage profile is compatible.
