# S3-compatible object-store ingestion runbook

Object-store ingestion is an optional document source for deployments that want
clients to upload large files directly to S3-compatible storage. It is additive:
local `/documents/upload`, `/documents/scan`, SDK text insertion, local
`INPUT_DIR`, and local parsed sidecars keep their existing behavior when this
feature is disabled.

The public third-party integration guide is published as a WebUI static page at
`/webui/docs/third-party-object-upload-integration/`. That page contains only
the integration flow and placeholder examples; it does not contain real
credentials, Secret names, or environment-specific connection details.

## Runtime configuration

Enable the feature explicitly:

```sh
LIGHTRAG_OBJECT_STORAGE=s3
S3_ENDPOINT_URL=https://minio-or-cos.example.com
S3_BUCKET=lightrag-documents
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
# Optional
S3_REGION=
S3_FORCE_PATH_STYLE=true
S3_OBJECT_PREFIX=lightrag/documents
S3_PRESIGN_TTL_SECONDS=900
S3_UPLOAD_SESSION_TTL_SECONDS=3600
S3_SCRATCH_DIR=/tmp/lightrag-object-scratch
```

Inject access credentials from a secret manager or Kubernetes Secret. Do not put
S3 credentials in `.env` files committed to source control, command lines, logs,
OpenSpec artifacts, or runbook evidence.

When `LIGHTRAG_OBJECT_STORAGE=s3` is enabled, startup initializes the upload
session KV namespace and runs an object-store preflight. Missing endpoint, bucket,
access key, secret key, or unusable bucket permissions fail closed; the server
does not silently fall back to local upload for object-backed requests.

## Client flow

1. Call `POST /documents/uploads/presign` with API authentication and a JSON body
   containing `filename`, `content_type`, `size`, and optional `checksum_sha256`.
2. Upload the file bytes directly to the returned `upload_url`, using the returned
   HTTP method and headers exactly.
3. Call `POST /documents/uploads/complete` with the returned `upload_id` and
   `object_key`.

The object key is generated by the server and is tied to the upload session and
workspace. Client-supplied object keys are ignored during presign and rejected on
completion if they do not match the issued session. Completion verifies the object
with `HEAD` before enqueueing the document.

`file_path` remains the user-visible source filename. The S3 bucket, key, size,
content type, checksum, ETag, upload id, and parsed-artifact prefix are stored in
`object_source` metadata.

## Processing and storage contract

Workers materialize the source object into `S3_SCRATCH_DIR`, pass that local
scratch path to the existing parser, then upload parsed sidecar artifacts back to
the object-store artifact prefix. Downstream analysis, chunking and retry resolve
remote `s3://bucket/prefix/` sidecar locations by mirroring them into local
scratch.

Object storage only holds source files and parsed artifacts. It does not replace
PG/pgvector, HugeGraph, KV/doc-status, vector storage, graph storage, LLM cache,
or any configured durable business storage.

## Kubernetes notes

For the object-backed distributed profile, use:

- shared PG/pgvector, HugeGraph, KV/doc-status configuration;
- `LIGHTRAG_OBJECT_STORAGE=s3`;
- `LIGHTRAG_SHARED_STORAGE=false` for the input-file path;
- Kubernetes Secrets for S3-compatible credentials;
- per-Pod `emptyDir` or other ephemeral storage for `S3_SCRATCH_DIR`.

Local `/documents/upload` and `/documents/scan` still need a filesystem visible to
the Pod that processes those local files. Removing the shared `INPUT_DIR` PVC is
safe only for acceptance paths that use the object-backed APIs.

## Cleanup and retry

- `DELETE /documents/delete_document` with `delete_file=true` removes the
  document's recorded server-owned source object and parsed-artifact prefix. It
  does not treat `file_path` as a local path for object-backed documents.
- Cleanup refuses keys outside LightRAG-owned upload/artifact prefixes and logs a
  diagnostic error instead of risking a broad bucket deletion.
- `POST /documents/reprocess_failed` reuses the recorded object source and remote
  sidecar metadata; the original client does not need to upload the file again.
- Expired, unfinished upload sessions can be listed and cleaned by the upload
  session manager. Cleanup touches only issued-but-uncompleted upload prefixes;
  completed document objects remain under document lifecycle control.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Presign returns 503 | Object store is disabled, missing configuration, or preflight failed. Check non-secret startup logs and Kubernetes Secret wiring. |
| Complete returns missing object | The client did not finish the direct PUT, used the wrong URL/headers, or uploaded to a different key. |
| Complete returns metadata mismatch | Compare declared size/content type/checksum with the object metadata; if a checksum was required, the object must expose the matching checksum metadata/header. |
| Parse retry keeps failing | Confirm the recorded object key still exists, the bucket policy permits read, and `S3_SCRATCH_DIR` has enough space. |
| Delete reports incomplete cleanup | Inspect the recorded object key/artifact prefix and bucket permissions. Do not manually delete broad prefixes without confirming ownership. |
