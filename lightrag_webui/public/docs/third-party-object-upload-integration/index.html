LightRAG 第三方 API 对接指南

本文面向要把 LightRAG 集成到业务系统中的第三方应用，覆盖认证、文档接入、处理状态、知识检索、图谱查询、运维探测、错误处理和端到端落库建议。对象上传只是其中一个推荐的大文件接入路径；登录页、WebUI 静态资源和内部调试路由不属于第三方业务对接 API。

本页面可公开访问，不包含任何真实密钥、对象存储凭据、内部 Secret 名称或环境专用连接信息。
公开文档 API 控制面需要认证 文件正文不经过 LightRAG API 对象 key 由服务端生成 查询与图谱接口独立说明

WebUI 路径：/webui/docs/third-party-object-upload-integration/。如果部署在网关前缀下，请在前面加站点前缀。

第三方系统与 LightRAG 的边界

业务系统负责

保存业务文件 ID、业务用户权限、上传会话与 track_id 的映射；决定什么时候允许用户查询、重试或删除。

LightRAG 负责

校验文档来源、异步解析与索引、提供 RAG 查询、返回引用、暴露图谱查询和运行状态。

对象存储负责

承接文件数据面。第三方应用只使用短时 upload_url 直传文件，不接触对象存储长期凭据。

推荐端到端顺序

1. 建立认证与租户映射按部署约定携带 X-API-Key，如使用多 workspace，业务系统先决定每次调用的目标 workspace。
2. 接入文档大文件优先走 presigned 对象上传；小文本可走 POST /documents/text 或 POST /documents/texts。
3. 等待异步处理完成保存 track_id，轮询 GET /documents/track_status/{track_id}，不要把 complete 成功当作可检索。
4. 发起知识检索调用 POST /query 或 POST /query/stream，按需要启用 references 和 chunk content。
5. 维护生命周期通过状态、失败重试、删除和 health API 做排障与运维闭环。

认证与通用约定

第三方应用调用 LightRAG 控制面 API 时，通常使用 X-API-Key；如部署启用了登录态，也可以使用有效 JWT。认证信息只应该保存在第三方服务端或安全网关中，不要下发给不可信客户端。

约定第三方必须遵守原因
认证所有业务调用统一带 X-API-Key: <your-lightrag-api-key>。避免匿名用户直接占用索引、查询和图谱资源。
路径前缀若网关配置了站点前缀，请在所有 endpoint 前拼接同一个前缀。同一套文档可用于根部署和多站点部署。
请求体普通 JSON API 使用 application/json；对象直传使用 presign 响应指定的 method 与 headers。LightRAG 控制面与对象存储数据面是两类请求。
workspace如服务端开放 workspace 选择，第三方要把业务租户映射到固定 workspace。文档、查询、图谱和状态必须在同一工作区内闭环。
重试对 429/503 做带退避的重试；对 400/401/403/404/409/422 先修正请求或业务状态。区分临时容量问题和不可通过重试修复的请求问题。
普通路由如 /query、/api/chat 有请求体和字段长度上限；大文件不要通过查询或聊天接口传输。

对象上传流程：一次文件上传从签名到可检索

这是文档接入章节中的推荐大文件路径。第三方应用通过 LightRAG 申请上传会话，文件数据面直接进入 S3-compatible 对象存储，随后由 LightRAG worker 异步解析与索引。

第三方必须按顺序完成的上传步骤

STEP 1申请上传会话调用 POST /documents/uploads/presign，只提交文件元数据；保存 upload_id 与 object_key。
STEP 2直传对象存储按 presign 响应中的 method、headers 和 URL 上传文件正文；该请求不经过 LightRAG API。
STEP 3完成确认调用 POST /documents/uploads/complete，由 LightRAG HEAD 对象并校验 session/key/size/type/checksum。
STEP 4轮询处理状态保存 complete 返回的 track_id，通过 GET /documents/track_status/{track_id} 等待文档可检索。
complete 成功只代表“已受理并入队”，不是“已经可查询”。查询 API 不负责等待 pipeline，也不会读取未处理完成的对象。

文档接入 API 详解

下面列出第三方可能用于文档接入的每个入口。新集成优先选对象上传；本地文件上传、scan 和文本插入保留为兼容或小文本场景。

#POST /documents/uploads/presign — 申请对象上传会话

1. 基本信息

接口名称
申请对象上传会话
请求路径
/documents/uploads/presign
请求方式
POST
接口状态
已上线；具体能力以当前部署配置为准。

功能说明：让 LightRAG 为单个待上传文件创建短时 upload session，并返回服务端生成的 object_key、预签名上传地址、必须携带的上传头、过期时间和本次允许的最大大小。这个接口只走控制面，不接收文件正文。

调用时机：第三方应用已经知道文件名、MIME 类型和字节大小，且希望浏览器或业务后端把文件直接上传到对象存储时调用。大文件、跨公网客户端上传、多 Pod 部署都应优先使用该接口，而不是把文件正文 POST 到 LightRAG。

接入建议：在业务库先创建“待上传”记录，保存 upload_id、object_key、源文件名和过期时间；不要保存或打印完整 upload_url。如果 URL 过期，重新申请 session，而不是拼接或猜测对象 key。

2. 请求参数（Request）

请求头：携带 X-API-Key 与 Content-Type: application/json；如部署改用 JWT，则按网关约定替换认证头。

请求参数：请求体为 JSON，至少包含 filename、content_type、size，可带 checksum_sha256。文件名必须是安全 basename，客户端不得传入自定义对象路径；认证头仍走 LightRAG 控制面认证。

参数名位置类型是否必填字段说明
X-API-KeyHeaderString是LightRAG 控制面认证凭证；如部署改用 JWT 或网关鉴权，请按部署方约定替换为等价认证头。
Content-TypeHeaderString是普通请求体固定使用 application/json；不要把文件正文放入 JSON 字段。
AcceptHeaderString否建议使用 application/json；流式接口可接收 application/x-ndjson 或 text/event-stream 形式的逐段输出。
filenameBodyString是用户原始文件名，只允许安全 basename；客户端不得传入目录、对象 key 或可逃逸路径。
content_typeBodyString是待上传文件 MIME 类型；必须和直传对象的 Content-Type 保持一致。
sizeBodyInteger是文件字节数；LightRAG 会按上限校验并在 complete 时与对象存储 HEAD 结果比对。
checksum_sha256BodyString否小写 SHA-256 摘要；提供后 complete 会校验，适合业务侧要求强完整性的场景。

3. 响应结果（Response）

返回格式：JSON 对象。

响应字段：返回 upload_id、object_key、upload_url、method、headers、expires_at、expires_in 与 max_size。响应不包含对象存储长期凭据；upload_url 只用于随后一次直传。

字段名类型字段说明
upload_idString服务端生成的上传会话 ID，complete 时必须原样回传。
object_keyString服务端生成的对象 key，第三方只保存和回传，不自行拼接。
upload_urlString短时预签名上传地址，只用于本次直传；不应写入业务日志。
methodString对象存储直传方法，通常为 PUT。
headersObject直传对象时必须携带的请求头，例如 Content-Type。
expires_atString上传会话过期时间，第三方应在过期前完成上传并调用 complete。
max_sizeInteger本次允许上传的最大字节数。
成功响应示例 
{
  "upload_id": "server-issued-upload-id",
  "object_key": "server/generated/object/key",
  "upload_url": "https://object-store.example/upload-token",
  "method": "PUT",
  "headers": {"Content-Type": "application/pdf"},
  "expires_in": 900,
  "expires_at": "2026-09-15T12:00:00+00:00",
  "max_size": 52428800
}

4. 状态码与异常说明

状态码错误原因排查建议
200创建成功保存响应中的业务 ID；对异步接口继续轮询状态，不要把受理成功等同于可检索。
400/422文件名、大小或 content type 不合法按参数表核对必填字段、类型、枚举值、路径参数和请求体格式。
401/403认证失败检查控制面认证头、网关鉴权策略和调用方权限。
413超过上传限制压缩文件、拆分批次或重新申请符合大小限制的上传会话。
503对象存储未启用或 preflight 不可用检查对象存储、数据库、向量库、图数据库、LLM 或 embedding 依赖是否可用。

5. 代码示例

cURL 示例 
curl -sS -X POST "https://<lightrag-host>/documents/uploads/presign" \
  -H "X-API-Key: <your-lightrag-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
  "filename": "report.pdf",
  "content_type": "application/pdf",
  "size": 1234567,
  "checksum_sha256": "optional-lowercase-sha256"
}'
请求体或 URL 示例 
{
  "filename": "report.pdf",
  "content_type": "application/pdf",
  "size": 1234567,
  "checksum_sha256": "optional-lowercase-sha256"
}

#POST /documents/uploads/complete — 完成对象上传并入队

1. 基本信息

接口名称
完成对象上传并入队
请求路径
/documents/uploads/complete
请求方式
POST
接口状态
已上线；具体能力以当前部署配置为准。

功能说明：通知 LightRAG 校验已经直传到对象存储的文件，并在对象存在、大小、content type、checksum 与上传会话匹配后写入文档状态，触发后续异步解析和索引。

调用时机：对象存储 PUT/POST 上传成功后立即调用。这个接口是从“文件已上传”进入“LightRAG 已受理处理”的唯一控制面确认点；仅上传到对象存储不会自动让文档可检索。

接入建议：把返回的 track_id 与业务文件记录绑定；complete 失败时保留 session 信息给用户重试或重新上传。不要在 complete 成功后立即开放问答入口，应轮询 track status 直到目标文档进入已完成状态。

2. 请求参数（Request）

请求头：携带 X-API-Key 与 Content-Type: application/json；如部署改用 JWT，则按网关约定替换认证头。

请求参数：请求体只需要回传 upload_id 与原样 object_key，可带 parser/chunking 等处理选项。LightRAG 会用 session 中记录的服务端事实做 HEAD 校验，客户端不能借此提交别的对象。

参数名位置类型是否必填字段说明
X-API-KeyHeaderString是LightRAG 控制面认证凭证；如部署改用 JWT 或网关鉴权，请按部署方约定替换为等价认证头。
Content-TypeHeaderString是普通请求体固定使用 application/json；不要把文件正文放入 JSON 字段。
AcceptHeaderString否建议使用 application/json；流式接口可接收 application/x-ndjson 或 text/event-stream 形式的逐段输出。
upload_idBodyString是presign 响应中的上传会话 ID；用于定位服务端保存的会话事实。
object_keyBodyString是presign 响应中的对象 key，必须原样回传；客户端不能替换成其他对象。
parserBodyString否解析器提示，例如 auto、native、mineru、docling；省略时由服务端按文件类型路由。
chunkingBodyObject否分块策略和参数；应与本系统允许的 parser/process 选项保持一致。

3. 响应结果（Response）

返回格式：JSON 对象。

响应字段：返回插入受理结果，通常包含 status、message、track_id、doc_ids 或等价字段。成功只代表进入 pipeline；可检索性必须继续通过状态接口确认。

字段名类型字段说明
statusString受理结果，通常为 success 或等价成功状态。
messageString人类可读提示，可用于操作结果提示但不应作为业务判断唯一依据。
track_idString后续查询异步处理状态的跟踪 ID。
doc_idsString[]本次入队涉及的 LightRAG 文档 ID 列表。
成功响应示例 
{
  "status": "success",
  "message": "Document upload completed and queued",
  "track_id": "upload_xxx",
  "doc_ids": ["doc-abc123"]
}

4. 状态码与异常说明

状态码错误原因排查建议
200校验并入队成功或幂等返回保存响应中的业务 ID；对异步接口继续轮询状态，不要把受理成功等同于可检索。
400/422请求字段不合法按参数表核对必填字段、类型、枚举值、路径参数和请求体格式。
404session 或对象不存在确认资源 ID、track_id、实体名、对象 key 或 upload session 仍存在且属于当前 workspace。
409session/key/workspace 冲突或同名文档冲突检查同名来源、并发操作、pipeline/admin 写入互斥或上传会话状态后再重试。
503对象存储或后端暂不可用检查对象存储、数据库、向量库、图数据库、LLM 或 embedding 依赖是否可用。

5. 代码示例

cURL 示例

  -H "X-API-Key: <your-lightrag-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
  "upload_id": "server-issued-upload-id",
  "object_key": "server/generated/object/key"
}'

  "upload_id": "server-issued-upload-id",
  "object_key": "server/generated/object/key"

#POST /documents/upload — 官方兼容文件上传

1. 基本信息

接口名称
官方兼容文件上传
请求路径
/documents/upload
请求方式
POST
接口状态
已上线；具体能力以当前部署配置为准。

功能说明：保留官方 multipart 文件上传入口。默认本地文件摄取启用时，LightRAG API 接收文件正文并写入服务器输入目录；object-store-only 部署关闭本地文件摄取且对象存储可用时，同一个接口会把文件写入对象存储并异步入队。

调用时机：第三方已经按官方 LightRAG API 集成 multipart 上传时可继续使用。大文件或高并发仍优先使用 presigned 对象上传；需要 object-store-only 部署时，无需改 API 路径，只要服务端已配置对象存储即可。

接入建议：新集成若能改造客户端，优先使用 presigned 对象上传以减少 API Pod 带宽占用。若保留官方上传，客户端只依赖外部请求/响应合同，不应假设后端写入本地目录还是对象存储。

2. 请求参数（Request）

请求头：携带 X-API-Key，并使用 multipart/form-data；boundary 由 HTTP 客户端生成。

请求参数：请求使用 multipart/form-data，字段通常为上传文件本身，可附带 parser、chunking 或 process 选项。文件名按官方上传规则校验，同名冲突按 canonical basename 处理；后端存储位置由部署配置决定。

参数名位置类型是否必填字段说明
X-API-KeyHeaderString是LightRAG 控制面认证凭证；如部署改用 JWT 或网关鉴权，请按部署方约定替换为等价认证头。
Content-TypeHeaderString是multipart/form-data，由 HTTP 客户端自动附带 boundary；官方兼容上传入口使用。
AcceptHeaderString否建议使用 application/json；流式接口可接收 application/x-ndjson 或 text/event-stream 形式的逐段输出。
fileFormFile是要上传的文件正文；API Pod 会承载该请求的数据面，后端可能写入本地输入目录或对象存储。
parserFormString否解析器提示；大文件新集成建议优先走 presigned 对象上传链路后再 complete。
chunkingFormObject/String否分块选项；如客户端以字符串传递，服务端需能解析为合法配置。

3. 响应结果（Response）

返回格式：JSON 对象。

响应字段：返回插入受理结果和 track_id；服务端已经完成持久入队，但解析和索引仍然是异步流程，必须查询状态确认。

字段名类型字段说明
statusString官方上传受理结果。
messageString上传或入队提示。
track_idString用于查询后续解析、抽取和索引状态。
成功响应示例 
{
  "status": "success",
  "message": "File uploaded successfully",
  "track_id": "upload_xxx"
}

4. 状态码与异常说明

状态码错误原因排查建议
200受理成功保存响应中的业务 ID；对异步接口继续轮询状态，不要把受理成功等同于可检索。
400/422文件名或处理选项非法按参数表核对必填字段、类型、枚举值、路径参数和请求体格式。
409同名文档冲突或 pipeline 控制面冲突检查同名来源、并发操作、pipeline/admin 写入互斥或上传会话状态后再重试。
413超过大小限制压缩文件、拆分批次或重新申请符合大小限制的上传会话。
503对象存储未配置或暂时不可用，且本地文件摄取不可用确认部署是否允许官方上传写入对象存储；稍后重试或联系平台侧排查对象存储 preflight。
500持久化或后端失败记录响应中的安全错误摘要和请求 ID，交由平台侧排查后端日志。

  -F "file=@report.pdf" \

#POST /documents/text — 插入单条文本

1. 基本信息

接口名称
插入单条文本
请求路径
/documents/text
请求方式
POST
接口状态
已上线；具体能力以当前部署配置为准。

功能说明：直接把一段已经在第三方系统中生成或抽取好的文本提交给 LightRAG，不需要文件上传、对象存储或 parser。LightRAG 会按文本内容创建文档并进入普通 chunk/extract/index 流程。

调用时机：业务系统已有纯文本、OCR 结果、表单摘要、工单内容或短知识片段时使用。它适合小体量文本和服务端同步生成内容，不适合把大文件全文塞入 JSON。

接入建议：把单条业务对象映射到一个稳定 file_source，避免每次重试生成不同来源名导致重复文档。超过普通 JSON 请求体的长文本应拆分为多条或改走文件/对象上传。

2. 请求参数（Request）

请求头：携带 X-API-Key 与 Content-Type: application/json；如部署改用 JWT，则按网关约定替换认证头。

请求参数：请求体包含 text，可选 file_source 作为业务可读来源名，可选 chunking 控制切分方式。file_source 应稳定且能回到业务对象，便于引用和删除。

参数名位置类型是否必填字段说明

错误处理

HTTP 状态常见原因建议处理
400 / 422参数为空、query 太短、文件名不安全、chunking 参数非法。提示用户或修正请求，不要原样重试。
401 / 403缺少或无效认证信息。检查服务端配置和调用方凭证。
404track_id、图谱对象或对象上传会话不存在。确认业务系统保存的 ID 是否正确。
409同名文档冲突、pipeline 正在执行扫描分类或破坏性任务、admin write 窗口冲突。向用户说明冲突；必要时删除旧文档后重新提交，或稍后重试。
413文件或请求体超过限制。文件走对象上传；文本批量拆分；查询输入缩短。
429待处理文档达到容量上限。按 Retry-After 或指数退避稍后提交。
503对象存储、存储后端或恢复栅栏暂不可用。进入降级；暂停写入，保留业务记录等待恢复。

第三方应用必须遵守的安全约定

  • ✓第三方应用只保存 LightRAG 控制面认证信息；对象存储服务端凭据永远不下发给第三方应用。
  • ✓upload_url 视为短时敏感材料，只在上传请求中使用，不写入日志和埋点。
  • ✓object_key 是服务端签发的对象标识，只能按响应原样回传。
  • ✓文件名必须是普通文件名，不允许路径穿越、控制字符或不安全字符。
  • ✓建议由第三方后端统一调用 LightRAG；浏览器直传对象存储时只使用短时授权，不接触长期凭据。

API_BASE="https://<lightrag-host>"
API_KEY="<your-lightrag-api-key>"

PRESIGN_JSON=$(curl -sS -X POST "$API_BASE/documents/uploads/presign" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"filename":"report.pdf","content_type":"application/pdf","size":1234567}')

UPLOAD_URL=$(printf '%s' "$PRESIGN_JSON" | jq -r '.upload_url')
OBJECT_KEY=$(printf '%s' "$PRESIGN_JSON" | jq -r '.object_key')
UPLOAD_ID=$(printf '%s' "$PRESIGN_JSON" | jq -r '.upload_id')

curl -sS -X PUT "$UPLOAD_URL" \
  -H "Content-Type: application/pdf" \
  --data-binary @report.pdf

COMPLETE_JSON=$(curl -sS -X POST "$API_BASE/documents/uploads/complete" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d "$(jq -n --arg upload_id "$UPLOAD_ID" --arg object_key "$OBJECT_KEY" '{upload_id:$upload_id, object_key:$object_key}')")

TRACK_ID=$(printf '%s' "$COMPLETE_JSON" | jq -r '.track_id')
curl -sS -H "X-API-Key: $API_KEY" "$API_BASE/documents/track_status/$TRACK_ID"

curl -sS -X POST "$API_BASE/query" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query":"请总结刚上传文档中的关键风险","mode":"mix","include_references":true}'

JavaScript/TypeScript：查询 API

async function askLightRAG(question) {
  const response = await fetch('https://<lightrag-host>/query', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'X-API-Key': '<your-lightrag-api-key>'
    },
    body: JSON.stringify({
      query: question,
      mode: 'mix',
      include_references: true,
      include_chunk_content: false
    })
  })

  if (!response.ok) throw new Error(`LightRAG query failed: ${response.status}`)
  return await response.json()
}
